# One eight-byte width guard for `number` (issue 9893)

**Spec:** `docs/superpowers/specs/2026-11-13-9893-width-guard-design.md` and
issue #9893.

## Global Constraints

- The new attribute is `number.checked`, defined once, in
  `eo-runtime/src/main/eo/number/checked.eo`, as `[^num] > checked`.
- Its body is one `if.` with three branches: `num.as-bytes.size.eq 8` →
  `number num.as-bytes`; otherwise
  `T "A number needs exactly 8 bytes, got %d".printf * num.as-bytes.size`.
  No second message anywhere in the five objects.
- `sqrt`, `ln`, `as-char` read `num.checked`; `power` reads `b.checked`;
  `mod` reads `b.checked` for `divisor` and `num.checked` for `dividend`.
- The named holders stay: `sqrt` keeps `num.checked >> arg`, `ln` keeps
  `num.checked >> n`, `power` keeps `b.checked >> expo`, `as-char` keeps
  `num.checked >> arg`, `mod` keeps `b.checked >> divisor` and
  `num.checked >> dividend`. None becomes a bare dispatch, because the
  following comparison would blame its own `b` (#9283).
- Out of scope, untouched: `is-finite` (`number/is-finite.eo:15`) and
  `is-nan` keep answering `false` for a wrong width; `eq` keeps comparing
  raw bytes; the atoms `plus`, `times`, `div`, `gt` keep their Java message
  from `Numeric`; `power`'s receiver (`base`) stays unchecked.
- No Java test is added: `CLAUDE.md` forbids Java tests for EO objects. Tests
  are `++>` / `-->` attributes inside `number/checked.eo`.
- `.eo` files keep the header (`+architect`, `+home`, `+package number`,
  `+spdx` twice, `+version 0.0.0`), 2-space indentation, and are left to the
  `format` goal of `eo:compile` as the source of truth for layout.
- Java 17; `mvn -Dmaven.repo.local=…/9893-m2/repository -pl eo-runtime test`
  stays green, and so does `mvn -Pqulice -pl eo-runtime verify`.

## Review Focus

1. **A wrong-width receiver must still terminate, not reach a Java atom.**
   `(number "abc").sqrt`, `.ln`, `.power 2`, `.as-char` must all terminate
   with the width message; `.mod 3` only where it reaches the quotient,
   because `mod` returns the receiver as it stands on the nan, infinity and
   zero-divisor paths. Test: `checked`'s own `-->` test plus the
   kept `as-char.eo` range tests.
2. **A wrong-width divisor in `mod` must terminate**, and it now terminates
   earlier: `divisor` is read by the first `if.` condition, so
   `42.mod (number 01-02)` fails at `checked` instead of at the old `'b'`
   branch. It must not fall into `cant-mod`. Test: the plan admits this is
   unassertable in EO (no supported way to read a termination message), so it
   is proven by `git grep` and by the task reviewer reading `mod.eo`.
3. **A correct 8-byte value must be untouched**, special chains included:
   `(number pinf.as-bytes).checked` is `pinf`, `(number nan.as-bytes)` is
   `nan`, `42.checked` is 42, `-0` keeps its sign. Test:
   `checked`'s `++>` test plus the existing suite.
4. **`mod`'s arithmetic must not change**: `-13.mod 5`, `7.mod 3`,
   `1000000000000000.mod 0.1`, `0.neg.mod 3` (negative zero), `-5.mod pinf`,
   `5.mod ninf`, the largest-double case. Test: the existing `mod.eo` tests.
5. **No other object's message changes**: `as-char` keeps its range message,
   `ln` keeps its nan answer, and `ExpectTest` (the Java `Numeric`, `Int`,
   `Natural` and atom `b` messages) is untouched. Test: `ExpectTest` and
   `as-char.eo`'s `stops-on-a-code-past-the-ascii-range`.
