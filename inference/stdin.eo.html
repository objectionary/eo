1# Convenient wrapper `stdin` on `console` object
2# which is used as input only and allows to read the data from console.
3#
4# To read just one line you can do:
5# ```
6# stdin.next-line
7# ```
8#
9# To read all lines you can do:
10# ```
11# stdin.all-lines
12# ```
13#
14# or just dataize `stdin` object.
15#
16# `all-lines` forces the current line's text through `seq` before the next
17# `line-or-eof` probe is even constructed. Both the accumulated text and
18# that probe read from the same console stream: constructing the probe reads
19# its own lookahead byte, and without this ordering that read races ahead of
20# the current line's own multi-byte read, since neither was otherwise forced
21# until the whole recursion bottomed out at the final `string`.
22#
23# That next probe is named through the root `stdin` and not through the
24# receiver, because an attribute answers with the very same object every
25# time it is taken: a probe taken twice from one `stdin` is one probe,
26# holding the one lookahead byte it has already read and the one line it has
27# already assembled. Through the receiver the recursion would see that same
28# line and that same `eof` at every level and never end, while the root
29# names a `stdin` of its own, whose probe reads the next byte of the stream
30# where the previous probe left off.
31#
32# Reading from the console cannot be exercised by a `++>` test, since
33# `console.read` reaches the process's real file descriptor 0 through
34# `posix`/`win32` and neither can be substituted in EO. The
35# `reads-*` snippets of `eo-integration-tests` feed real standard input to a
36# forked JVM and check what comes back.
