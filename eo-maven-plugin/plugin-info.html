Plugin Details

This report describes goals, parameters details, requirements and sample usage of this plugin.

Goals

Goals available for this plugin:

Goal Description
eo:assemble Pull all necessary EO XML files from Objectionary and parse them all.

This goal combines MjParse, MjProbe and MjPull. See their documentation to find out more details. The runs these goals repeatedly until no new objects are pulled or parsed in a cycle.

eo:clean Implementation of maven clean plugin, just deleting target/eo directory.

This goal simply deletes the directory containing all the files used for compilation.

eo:compile Compile and lint all EO files.

This goal combines MjAssemble, MjLint, MjMerge, MjResolve and MjPlace goals. See their documentation to find out more details. The is useful to run the whole compilation process in one go without the need to call each goal separately.

The merge happens right after the lint, so that every goal between this one and MjTranspile that reads an object through its tojo, such as MjDealpha and MjLower, reads it in the shape it will be compiled in and not in the shape the parser left. A project therefore never has to name merge between them, and naming it changes nothing: a member already inside its object is not moved again.

MjInfer reads the files the parser wrote, one per source, and not the merged ones, for the reasons its own documentation gives. Its tables still fit the merged objects: the parser gives every object the locator it will carry once it is inside its package object, and the merge moves none of them.

eo:dealpha Mojo that gives the positional arguments of a program the names of the voids they land in, right after the inference goal.

The parser has no way to know which void an argument fills, so it names them by their places: in foo k, the k is α0. The answers.xml of MjInfer knows better, since the row of an argument names the void it lands in whenever there is one. This goal reads it and writes foo (bar: k) instead, wherever the answer is certain, as described in #8301:

 <o loc="Φ.app.φ.α0" copies="1" lands="bar">
  <is loc="Φ.number"/>
</o>

The row says that Φ.app.φ.α0 is bar. The engine writes the name only when every application it saw puts the argument into one void and nowhere else. An argument has no lands when it lands in two voids, or when the engine cannot tell which formation the application is made on, such as an unknown or an object made in Java.

The engine sees only the applications written in the program, and that is enough: EO always compiles the whole program, so there is no other program that could attach something else to a void. When another program appears, the compiler and the engine run again (#10056).

An argument keeps its place where no single void is known to take it, and the number of those is written to the log. With rigid set, the build fails when there is one.

The XMIR goes to a directory Seqdir numbers "dealpha", and MjTranspile reads it from there.

eo:format Enforce the canonical layout of .eo sources.

This goal walks through all registered .eo sources (see MjRegister), reformats every one of them in memory by parsing it to XMIR and printing it back with org.eolang.printer.Xmir.toEO() until the text stops changing (the moniker merge of #5739 is not a single-pass fixpoint, so the canonical form is the fixpoint of parse-and-print), and compares that against what is on disk. In its default "check" mode, it prints a colored unified Diff for every file that diverges from the canonical form and fails the build. When autofix is turned on (via the eo.format.autofix property), it overwrites the divergent files with their canonical form instead of failing, much like gofmt -w or spotless:apply.

Parsing a source is by far the costliest thing this goal does, so it does it as few times as it can: the sources are checked concurrently, through Threaded, the way every other goal walks them, and each settling pass keeps the tree it parsed instead of parsing the same text again to lay it out.

Every source is decoded strictly before Raws is asked for a tree, so a file that is not UTF-8 fails with its own name and line instead of being formatted from a tree the raw cache holds for an earlier text of the path.

eo:help Display help information on eo-maven-plugin.
Call mvn eo:help -Ddetail=true -Dgoal=<goal-name> to display parameter details.
eo:infer Mojo that reads what a program says about its own objects, preferably after the assemble goal.

What a program says about its objects is written down into facts.xml, which a later goal can read. In this program, for example, t has next, the object attached to next has nothing, and inc reads foo off whatever it is given:

 [] > app
  inc t > @
  [] > t
    [] > next
  [x] > inc
    x.next.foo > @

One pass through the XMIR of every file parsed so far writes every formation with its attributes, every name read and what it is read off, the head of every chain, and every call with its arguments.

Nothing here says whether the program is wrong. Judging it was written and taken out again in #6661, because a verdict needs the object that misses an attribute to have been seen whole, and almost none of them have been; the program has to be described before anything can read it for mistakes.

The XMIR of every registered source is read, and not every file the parse directory holds: a source that was deleted leaves its XMIR behind, and the facts would go on describing an object nobody wrote any more (#9271). Where each one lies is worked out from the identifier of the tojo, and not read off its xmir attribute, because eo:merge moves that attribute of a package object into the merge directory, while the facts are made of what the parser wrote.

The engine then reads facts.xml and writes answers.xml beside it: for every place, which objects it can be when Java runs the program. It has to know three lists of names of the program, which are parameters here: canon, roots and scalars. Almost every program is compiled together with eo-runtime, so a list left unset or empty holds the names of eo-runtime (#10079), and a program that has other names sets its own. Maven gives an empty list, not null, to a list parameter nobody sets, so empty means unset here. The names of eo-runtime do no harm to a program that has none of these objects: the canon is made only when every kind of it is there, and the other names then match nothing.

The prepared XMIR is saved in prepared, and facts.xml and answers.xml in tables. Nothing of it fails the build.

eo:lint Mojo that runs all lints and checks errors and warnings, preferably after the assemble goal.

This goal goes through all XMIR files generated in the previous steps (see MjParse or MjPull goals) and runs all available lints on them. If any errors or warnings are found, they are logged to the console, and depending on the configuration, the build may fail. The linting results are also embedded back into the XMIR files for future reference. Lints might use caching to speed up the process on subsequent runs. Cached files are stored in the Linting.CACHE directory. The results of linting are saved in a directory Seqdir numbers "lint".

eo:lower Fold the formations of a program into Java atoms.

A formation whose behaviour is decided at compile time pays the full cost of the object graph at runtime, for an answer the compiler could have known. Lowering computes such a formation through the external phino binary, which is the only thing here that knows the calculus, and keeps the answer as the body of a Java atom, so that the graph is never built while the program runs.

This goal is the entry point of that pipeline. It runs after render, by which time a program has said everything the lowering needs to hear about it, and before transpile, the last moment at which the Java of a program can still be changed.

The goal folds by default; -Deo.lower.bypass=true turns it off. When phino cannot be started on this computer, the goal prints a warning and does nothing, so the build goes on without atoms. With -Deo.lower.optional=false the goal fails the build instead. When it runs it makes sure that the binary on this machine is the one the pin names, since an answer of another version cannot be trusted, and then plants the entries of the build. It hands the lowering the XMIR of every standalone object, the directory where eo:infer left its tables, because an entry is a formation applied to what the tables say its voids hold, and one home directory, which Seqdir numbers as NN-lowering. There the lowering keeps the world, the sources with their tests cut out in 1-planting, and the protocol of every object morphed in 2-protocols. The atoms the lowering renders land in the numbered atoms directory, which this goal finds and hands to javac as a source root, and every XMIR file with an atom in the place of a body lands in the numbered patched directory, where this goal points the tojo of that object, so the transpiler reads the patched copy and every other object stays where it was. The copies stay from build to build, so only a copy listed in patched.tsv, one patched in this very build, is handed to the transpiler.

With -Deo.lower.minutes=true the lowering also keeps the protocol of every entry as indented text, called its "minutes", in the numbered minutes directory, beside 2-protocols, so a person can read why an entry stopped where it did without any tool. The same run of phino writes both, so no entry is computed twice.

eo:measure Turns the raw loc:line:pos coverage hits PhCoverage appended at runtime into an LCOV tracefile.

Bound to the verify phase, after the tests that actually populate the raw hits file have run (unlike transpile, which only decides whether locations get wrapped in PhCoverage in the first place, long before any test executes). Does nothing when eo.measure.hits is not set or the file does not exist yet, the same "no-op when disabled" contract PhCoverage itself follows, unless eo.measure.minimum is above zero: then the build fails, because a gate that measured nothing must not pass.

Every .eo file is re-parsed from its own source instead of reading the xmir stored in its tojo, because that xmir is the MjMerge one for a package root and mixes the members it spliced in, whose lines refer to their own files. Reporting those members' locations against the package root puts lines of unrelated files where the package's meta directives are, so each file is covered under its own name (they all carry @loc with the Φ prefix of the object they name, so the runtime hits still line up).

Every registered .eo file gets a record of its own, even one the manifest names no location in: a file of nothing but atom declarations and unit tests, like bytes.eo, has no dataizable body at all. Such a file used to be absent from the tracefile altogether, which left the report unable to tell it apart from a file that was never compiled (#7057).

The raw hits are read one line at a time and never held together in memory. What the report keeps out of them is one counter per line of source, so its own size is bounded by the manifest, but the file the runtime appends to is not: a location is written once per generated class per JVM, so every surefire fork appends its own copy of the few thousand distinct locations, and while every PhCoverage wrapper still started a dedup set of its own (#6508), a whole test suite left gigabytes of duplicates behind. Reading that file into a list first is what killed the eo-runtime coverage build with an OutOfMemoryError once it outgrew the 4Gb heap .mvn/jvm.config gives Maven.

eo:merge Put every member of a package inside the object that the package names.

An object and the package of the same name are two things today, and it takes the runtime to join them: asked for an attribute it does not hold, Φ.number goes looking for Φ.number.lt on the classpath and binds itself into the first void of what it finds. This goal does that joining at compile time instead, where the parts are already on disk as XMIR, so that lt is simply an attribute of number and nothing has to be searched for at runtime.

It runs after MjLint, so that every member is read and reported on as the file a human wrote, and before MjTranspile, which is the first goal that cares about the shape of the object it compiles. The merged XMIR goes to a directory Seqdir numbers "merge".

Every package this build compiles an object for is merged. A package whose name no object carries keeps its members as objects of their own, reached through the package namespace as before.

MjCompile runs the same step right after its lint, and MjTranspile runs it again before it writes anything, so a build that never names this goal still compiles merged objects, and every goal between the two reads them merged. Naming it anyway costs nothing: a member already inside its object is not moved again.

eo:parse Parse EO to XML.

This is the initial goal that parses all found EO sources to XMIRs. You can read more about XMIR format here

The goal scans all the EO sources registered in the foreign file catalog (see MjRegister and MjPull) and then parses those that were not parsed before (i.e. do not have XMIRs yet) to XMIR format. The resulting XMIR files are stored in a directory Seqdir numbers "parse".

eo:place Take binary files from where MjResolve placed them and copy to the target/classes directory.

Input directory is a directory Seqdir numbers "resolve". Output directory is target/classes.


See also: Place catalog
eo:print Print XMIR to EO.

This goal goes through all XMIR sources found in the specified directory, converts them back to EO format, and saves the resulting EO files in the specified output directory, preserving the original directory structure. Input XMIR files are found in sources, output EO files are saved in output.

eo:probe Go through all `probe` and `also` metas in XMIR files, try to locate the objects pointed by `probe` in Objectionary, and if found, register them in the catalog. More about the purpose of this Mojo is in this issue.

This goal just modifies the "foreign" catalog by adding newly discovered objects to it. It does not download or pull the sources of these objects, that is the job of MjPull goal which usually goes after this one. This goal does not create any files on the disk either.

eo:pull Pull EO files from Objectionary.

This goal goes through all objects from "foreign" catalog and looks for those without sources and pulls them from Objectionary remote repository. The pulled sources are stored in a directory Seqdir numbers "pull".

eo:register Find and register all .eo sources in the "foreign" catalog.

This goal scans the <sources> directory for all .eo files matching the inclusion and exclusion GLOB filters specified in the <register.included> and <register.excluded> parameters respectively. By default, it includes all .eo files found recursively. Each found EO source is then registered in the "foreign" catalog that later processed by other goals like MjParse, MjAssemble or MjCompile. This goal only changes the "foreign" catalog and does not save any generated files.

eo:render Draw a page per source file from what MjInfer wrote.

A page shows the author's own source with a mark on every object, coloured by one of nine bands of what the engine answers there in answers.xml: green where it answers one name and nothing else, other colours where it answers several names, names with gaps, an unknown of one of four kinds, or only errors. An index lists the pages with a bar per file, and the goal logs how many objects fall in each band and writes the same numbers down in ladder.txt, beside the directory of the tables.

A goal of its own rather than a flag on MjInfer: a build that wants the pages asks for this goal, one that does not never runs it.

eo:resolve Find all required runtime dependencies, download them from Maven Central, unpack and place to the target/eo directory.

The motivation for this mojo is simple: Maven doesn't have a mechanism for adding .JAR files to transpile/test classpath in runtime.

This goal goes through all dependencies found in the MjPull goal, finds their implementations (i.e. transitive dependencies), downloads them from Maven Central, unpacks them and places the resulting files to a directory Seqdir numbers "resolve".

eo:tabulate Generate the atom return types table from XMIR sources.

Walks the XMIR sources in sources, extracts the forma of every lambda atom together with its declared return type, and writes the result as a CSV file at csv. Each output line has the form <forma>,<return-type>; entries are sorted by forma to make the file stable across builds. A return type that is a tree, such as Φ.posix.status-return(Φ.number,Φ.string), is written as the name before its brackets, since the runtime checks only that name.

eo:transpile Transpile.

This Maven Mojo transpiles XMIR files into Java source files. The goal of this class is to automate the process of transforming EO intermediate representations (XMIRs) into Java code, optimize the output, and integrate the results into the Maven build lifecycle for further processing.

This is one of the final goals that transpiles XMIRs to Java files generated by MjAssemble, MjParse or MjPull goals. The resulting Java files are stored in a directory Seqdir numbers "transpile". The intermediate optimized XMIRs are stored in a directory Seqdir numbers "pre-transpile".

Before anything is written, the members of every package this build compiles an object for are put inside that object, the way MjMerge does it. The two are the same step and running both changes nothing, since Merging leaves a merged member alone; it is done here as well because the shape of an object decides the name of the Java class of every atom it holds, and a build that skipped the goal would name classes that the library it compiles against does not carry. An atom string.foo.bar ships as EOstring$EOfoo$EObar, which is where it lands once foo is an attribute of string, and nowhere near the org.eolang.EO_string package an unmerged +package string would compile it into (#8295).

eo:unplace It deletes binary files, which were previously copied by "place" mojo so these binaries are not got into result JAR.
eo:unspile Goes through all .class files and deletes those that were created from autogenerated sources so these binaries are not got into result JAR.

Usage

You should specify the version in your project's plugin configuration:

<project>
  ...
  <build>
    <!-- To define the plugin version in your parent POM -->
    <pluginManagement>
      <plugins>
        <plugin>
          <groupId>org.eolang</groupId>
          <artifactId>eo-maven-plugin</artifactId>
          <version>0.63.6</version>
        </plugin>
        ...
      </plugins>
    </pluginManagement>
    <!-- To use the plugin goals in your POM or parent POM -->
    <plugins>
      <plugin>
        <groupId>org.eolang</groupId>
        <artifactId>eo-maven-plugin</artifactId>
      </plugin>
      ...
    </plugins>
  </build>
  ...
</project>
